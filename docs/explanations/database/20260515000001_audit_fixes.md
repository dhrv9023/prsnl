# 20260515000001_audit_fixes.sql

**Location:** `prsnl/supabase/migrations/20260515000001_audit_fixes.sql`  
**Type:** Database Migration

## What This File Does

Fixes security issues identified in the May 2026 audit. Re-creates `handle_new_user` to ensure credits start at 0, adds a `user_id` column to `ai_analyses` for direct RLS protection, enables RLS on `ai_analyses` with proper policies, and documents the IP claim FK behavior fix.

## How It Fits Into The System

- **Triggers:** Run after `20260513000000_credit_system.sql` in migration order. Applied via `supabase db push` or `supabase migration up`.
- **Dependencies:** Requires the `profiles` table, `auth.users`, `ai_analyses` table, and `resumes` table to exist. Depends on the credit system migration having run first.
- **Dependents:** The frontend's analysis history queries now filter by `ai_analyses.user_id` directly (faster than joining through resumes). The RLS policies protect analysis data at the database level regardless of API bugs.

## Code Breakdown

### Section 1: Fix handle_new_user Trigger

Re-creates the `handle_new_user` trigger function with identical logic to the credit system migration version:

- Ensures `remaining_credits = 0` on new profile creation.
- Uses `ON CONFLICT (id) DO UPDATE` for idempotent behavior.
- This section exists as a safety net — if migrations run out of order or the credit system migration is skipped, this ensures the secure default (0 credits) is still applied.
- The function is `CREATE OR REPLACE`, so it overwrites any previous version without error.

### Section 2: Add user_id to ai_analyses

This is the main security fix. Previously, `ai_analyses` only linked to users through the `resumes` table (analyses → resumes → profiles). This indirect relationship made RLS policies complex and error-prone.

**Changes:**
- `ADD COLUMN IF NOT EXISTS user_id UUID REFERENCES auth.users(id) ON DELETE CASCADE` — direct FK to the user.
- **Backfill:** Updates all existing `ai_analyses` rows by joining to `resumes` to populate `user_id` from the resume's owner.
- **Index:** Creates an index on `user_id` for fast filtered queries.
- **RLS enabled:** `ALTER TABLE ai_analyses ENABLE ROW LEVEL SECURITY`.
- **Policies:**
  - `"Users can view own analyses"` — SELECT where `auth.uid() = user_id`.
  - Service role INSERT policy — backend can write new analyses.
  - Service role DELETE policy — backend can clean up analyses.

### Section 3: Resume Count Constraint Documentation

This section contains comments only (no DDL executed). It documents the design decision that `MAX_RESUMES_PER_USER = 20` is enforced at the application layer (FastAPI), not as a database constraint.

**Rationale documented:**
- A CHECK constraint can't easily count rows in another table.
- A trigger-based approach was considered but rejected for simplicity.
- The app-layer check in the resume upload endpoint is sufficient since all uploads go through the API.

### Section 4: ip_credit_claims FK Fix Documentation

This section contains commented-out ALTER statements and documentation about the FK behavior on `ip_credit_claims`:

**The issue:** If the original `ip_credit_claims` table was created with `ON DELETE CASCADE` on the `user_id` FK, then deleting a user would delete their IP claim record — allowing that IP to claim credits again on a new account (re-farming).

**The fix:** The FK should use `ON DELETE SET NULL` so the IP record persists (with a NULL user_id) even after user deletion. The commented-out SQL shows:
```sql
-- ALTER TABLE ip_credit_claims DROP CONSTRAINT ...;
-- ALTER TABLE ip_credit_claims ADD CONSTRAINT ... ON DELETE SET NULL;
```

This is left commented because it depends on how the original table was created — if it already uses SET NULL, no action is needed.

## Things To Know Before Editing

- This migration is fully idempotent — uses `ADD COLUMN IF NOT EXISTS`, `DROP POLICY IF EXISTS` before `CREATE POLICY`, and `CREATE OR REPLACE FUNCTION`. Safe to run multiple times.
- The `ai_analyses` backfill UPDATE (`SET user_id = resumes.user_id FROM resumes WHERE ...`) may be **slow on large tables** — it does a full table scan with a join. Consider running during low-traffic periods on production.
- The `ip_credit_claims` FK fix is **commented out** — you must manually uncomment and run it if your original table used `ON DELETE CASCADE`. Check with: `\d ip_credit_claims` in psql.
- Sections 3 and 4 are **documentation-only** — they contain no executable DDL. Don't expect them to create or modify any objects.
- After this migration, queries to `ai_analyses` without a WHERE clause on `user_id` will return empty results for authenticated users (RLS filters automatically). Service role bypasses RLS.
