# 20260513000000_credit_system.sql

**Location:** `prsnl/supabase/migrations/20260513000000_credit_system.sql`  
**Type:** Database Migration

## What This File Does

Implements the complete credit system in PostgreSQL. Adds credit columns to profiles, creates the `ip_credit_claims` table (anti-farming), creates the `credit_transactions` audit table, and defines two atomic RPC functions (`deduct_credits` with FOR UPDATE row lock, `grant_credits`). Also updates the `handle_new_user` trigger to start credits at 0 (the app layer grants credits after IP check).

## How It Fits Into The System

- **Triggers:** Run via `supabase db push` or `supabase migration up` during deployment. The `handle_new_user` trigger fires automatically on every new auth signup.
- **Dependencies:** Requires the `profiles` table and `auth.users` to already exist. Assumes Supabase auth is configured.
- **Dependents:** The FastAPI backend calls `deduct_credits` and `grant_credits` RPCs via Supabase client. The frontend reads `remaining_credits` and `is_unlimited` from profiles. The `/claim-credits` endpoint writes to `ip_credit_claims`.

## Code Breakdown

### Section 1: ALTER TABLE profiles

Adds three new columns to the existing `profiles` table:

- `remaining_credits` (INTEGER, DEFAULT 0) — the user's current spendable balance.
- `total_credits_granted` (INTEGER, DEFAULT 0) — lifetime total of credits received (for analytics).
- `is_unlimited` (BOOLEAN, DEFAULT FALSE) — bypass flag for admin/premium users.

After adding columns, the migration backfills all existing users with 100 credits (both `remaining_credits` and `total_credits_granted`). Then sets `is_unlimited = true` for any user whose profile is marked as admin. This ensures existing users aren't broken when the credit system goes live.

### Section 2: ip_credit_claims Table

Creates the anti-farming table that prevents a single IP address from claiming free credits on multiple accounts:

- **PRIMARY KEY** is the IP address itself (TEXT) — one row per IP, ever.
- `user_id` references `auth.users` — which account claimed credits from this IP.
- `granted_amount` (INTEGER) — how many credits were given.
- `claimed_at` (TIMESTAMPTZ) — when the claim happened.

The FastAPI `/claim-credits` endpoint checks this table before granting initial credits. If the IP already has a row, the claim is rejected.

### Section 3: credit_transactions Table

The audit log for every credit movement in the system:

- `id` — UUID primary key (gen_random_uuid).
- `user_id` — FK to `auth.users`.
- `feature` — TEXT identifying what consumed/granted credits (e.g., "resume_analysis", "initial_grant").
- `credits_used` — INTEGER, positive for deductions, negative for grants.
- `credits_before` — balance before the transaction.
- `credits_after` — balance after the transaction.
- `metadata` — JSONB for arbitrary context (resume ID, analysis type, etc.).
- `created_at` — TIMESTAMPTZ with default now().

**Indexes:**
- `(user_id, created_at DESC)` — fast retrieval of a user's transaction history in reverse chronological order.
- `(feature)` — analytics queries filtering by feature type.

### Section 4: deduct_credits RPC

The core spending function. Called by the backend whenever a user consumes credits:

```
deduct_credits(p_user_id UUID, p_feature TEXT, p_amount INT, p_metadata JSONB)
RETURNS JSONB
```

- **SECURITY DEFINER** — runs with the function owner's permissions (service role), not the caller's.
- Acquires a **FOR UPDATE** row lock on the user's profile row — concurrent requests queue rather than race.
- **Bypass for unlimited users** — if `is_unlimited = true`, returns immediately with `{ok: true, remaining: -1, unlimited: true}` without decrementing.
- **Insufficient balance check** — if `remaining_credits < p_amount`, raises an exception with message `'insufficient_credits'`. The FastAPI layer catches this and returns a 402 response.
- On success: decrements `remaining_credits`, inserts an audit row into `credit_transactions`, returns `{ok: true, remaining: <new_balance>, unlimited: false}`.

### Section 5: grant_credits RPC

The credit-adding function. Called when granting initial credits, admin top-ups, or promotional credits:

```
grant_credits(p_user_id UUID, p_amount INT, p_feature TEXT, p_metadata JSONB)
RETURNS JSONB
```

- **SECURITY DEFINER** — same elevated permissions pattern.
- Acquires **FOR UPDATE** lock on the profile row.
- Increments both `remaining_credits` and `total_credits_granted` by `p_amount`.
- Inserts an audit row with **negative** `credits_used` value (convention: negative = income).
- Returns `{ok: true, remaining: <new_balance>}`.

### Section 6: admin_set_unlimited Helper Function

A convenience function for toggling a user's unlimited status:

```
admin_set_unlimited(p_user_id UUID, p_unlimited BOOLEAN)
```

Simply updates `profiles.is_unlimited` for the given user. Used by the admin panel.

### Section 7: Updated handle_new_user Trigger

Replaces the existing `handle_new_user` trigger function:

- Fires on `INSERT` into `auth.users`.
- Creates a profile row with `remaining_credits = 0` (not 100).
- Uses `ON CONFLICT (id) DO UPDATE` for idempotent behavior — if the profile already exists (e.g., from a previous partial signup), it updates rather than failing.
- Credits start at 0 because the FastAPI app is responsible for granting initial credits after verifying the user's IP hasn't already claimed.

### Section 8: RLS Policies

Row Level Security configuration:

- **credit_transactions:**
  - Users can SELECT their own rows only (`auth.uid() = user_id`).
  - Service role has full access for INSERT (backend writes audit records).

- **ip_credit_claims:**
  - No direct user access — service role only.
  - Users cannot read or write this table through the Supabase client.

- **Grants:**
  - SELECT on `credit_transactions` to authenticated role.
  - EXECUTE on `deduct_credits`, `grant_credits`, `admin_set_unlimited` to service_role (and authenticated where appropriate).

## Things To Know Before Editing

- The `deduct_credits` function uses `FOR UPDATE` which means concurrent requests for the same user will **queue**, not fail. This prevents race conditions but can cause slight latency under heavy concurrent usage for a single user.
- The `grant_credits` function records `credits_used` as **negative** — this is intentional for display as income in transaction history. Don't "fix" this.
- The `handle_new_user` trigger starts credits at **0** — the FastAPI app layer is responsible for granting initial credits after the IP check. If you change this to grant credits directly, you bypass anti-farming protection.
- Running this migration twice is safe — it uses `IF NOT EXISTS` for table creation and `CREATE OR REPLACE` for functions.
- The backfill (existing users → 100 credits) only runs once because subsequent runs find the columns already exist and skip the ALTER.
- If you modify `deduct_credits` to return `{ok: false}` instead of raising an exception, you must also update the FastAPI error handling which catches the PostgreSQL exception.
