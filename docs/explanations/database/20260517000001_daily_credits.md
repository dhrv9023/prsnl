## What This Migration Does

This migration implements the database infrastructure for the **Daily Credit Grant System**. Users receive a daily credit top-up of **50 credits** once their initial 100-credit registration allocation is exhausted. To support this safely, this migration:
1. Creates the `public.daily_credit_grants` table to log daily top-ups.
2. Implements a **unique user-date constraint** to guarantee that a user cannot receive multiple grants on the same calendar day.
3. Configures Row-Level Security (RLS) policies.
4. Adds the `last_daily_grant_date` column to `public.profiles` for fast eligibility verification.

## How It Fits Into The System

- **What triggers it:** Applied during database setup. Once active, backend cron jobs or dynamic logins check this table to verify eligibility and grant top-ups.
- **What it depends on:**
  - `auth.users` — references user accounts with cascade deletions.
  - `public.profiles` — adds helper columns.
- **What depends on it:**
  - FastAPI credits checking layer — performs quick reads of `last_daily_grant_date` to check if a top-up is due.

## Code Breakdown

### `daily_credit_grants` Table
**Lines:** 15–25  
Creates the transaction record table:
- `id` (UUID, PRIMARY KEY).
- `user_id` (UUID, references `auth.users(id) ON DELETE CASCADE`).
- `grant_date` (DATE) — records the UTC calendar date (excluding times) of the grant.
- `amount` (INTEGER, defaults to 50).
- **`daily_credit_grants_user_date_unique` constraint**: A critical composite unique constraint:
  ```sql
  CONSTRAINT daily_credit_grants_user_date_unique UNIQUE (user_id, grant_date)
  ```
  This is the primary security layer preventing race-conditions or duplicate grants. Even if multiple fast requests hit the server, PostgreSQL rejects any duplicates at the database layer.

### Row Level Security (RLS)
**Lines:** 31–43  
- **`Users can view own daily grants`**: Authenticated users can query their own top-up log.
- **`Service role can insert daily grants`**: Only the system backend can insert top-up transactions.

### Fast Eligibility Cache Column
**Lines:** 45–47  
```sql
ALTER TABLE public.profiles
    ADD COLUMN IF NOT EXISTS last_daily_grant_date DATE;
```
Caching this date directly in the profile table allows the backend to check eligibility in a single query during login, eliminating the need to search the entire `daily_credit_grants` history table.

## Things To Know Before Editing

- **Non-Cumulative Policy:** The backend grant code uses this architecture to top up the balance **TO 50** rather than adding on top, ensuring that inactive users do not accumulate large pools of unused credits.
- **UTC Alignment:** The `grant_date` uses PostgreSQL's `DATE` format aligned to the **UTC calendar day**. Do not write timezone-specific timestamps into this column, as it could disrupt date matching calculations.
- **Exemptions:** Premium or unlimited accounts are exempt from this daily limit checking sequence.
